# Stage 2 最小プロトタイプ設計

作成: 2026-11-24 / 根拠: docs/stage2-research.md（技術調査）
目的: Stage 2（見た目）・Stage 3（関節）の本実装に入る前に、「カスタムジオメトリが統合版に表示され、プロパティでボーンが動く」最小構成の足場を固める。

## 全体構成（3点セット）

1. **Paper プラグイン**（現行 ViveBridge の拡張）: VSE からポーズ取得 → 関節角度を計算 → Geyser 拡張へ送信
2. **Geyser 拡張**: 起動時にカスタムエンティティ定義とプロパティ型を登録。プラグインからの角度値を受けてプロパティを上書きする
3. **Bedrock リソースパック**: 人型ジオメトリ（Java版スキンの UV 配置を再現）+ テクスチャ（本人のスキン）+ Molang でプロパティを読むアニメーション

- プラグインと拡張は**同一 jar の別エントリポイント**とし、連携はプラグインメッセージで行う（実績構成 RSPM と同方式）
- キャリアは現行の防具立てマネキンを流用する（Custom Entity API は「Java エンティティの Bedrock 表現の置き換え」方式）

## 先に潰す未確認事項（S2-0 の前提）

1. ~~使用中 Geyser ビルド（2.12.1-b1307）に Custom Entity API のクラス群が含まれているか~~ → **確認済み（2026-11-24）**: 同一ビルドの jar を取得してクラス一覧を確認。`CustomEntityDefinition`、登録イベント `GeyserDefineEntitiesEvent`、プロパティ API（`GeyserFloatEntityProperty` / `BatchPropertyUpdater`）の存在を確認（詳細は stage2-research.md の追記）
2. ~~登録イベントとプロパティ上書き API の正確なシグネチャ~~ → **ほぼ確定（2026-11-24、javap で一次確認）**: 登録は `GeyserDefineEntitiesEvent.register`、プロパティ登録は `GeyserDefineEntityPropertiesEvent.registerFloatProperty(対象Identifier, 名前, min, max, 既定値)`、更新は `GeyserEntity.updateProperty / updatePropertiesBatched`（詳細は stage2-research.md 追記2）
3. **キャリアの割り当て方式**: `SessionSpawnEntityEvent` に definition の setter があり、**スポーン個体ごとに定義を差し替えられる**ことを確認（2026-11-24）。識別は **UUID 照合で確定**: `ServerSpawnEntityEvent` 自体が `uuid()` / `entityId()` / `entityType()` を返すため、プラグインが生成時に登録したマネキン UUID と照合し、一致した個体だけ `definition()` で差し替える（2026-11-24 確認）。登録はスポーン呼び出しと同期して行い、取りこぼしを防ぐ
   - **注意（ミーナのレビュー指摘, 2026-11-24）: scoreboard tag は Java クライアントに送られないため Geyser 側からは見えない**。目印に使えるのは Geyser が変換するメタデータ（名前・フラグ・装備など）に限られる。名前は本人名入りで脆いので、防具立てのフラグの組み合わせ（例: marker + 腕あり + ベースプレートなし等）や特定の装備を目印にする案を優先して確認する
   - それも無理なら、防具立て以外のエンティティタイプをキャリアにする案が残る

## プロパティ設計（起動時登録のため先に固定する）

角度はすべて float、range **[-360, 360]**、`client_sync: true`、読み取りは `q.property('名前')`。
- **range を広げる理由（ミーナのレビュー指摘）**: 腕を真上に上げると角度が ±180° の境界に乗り、符号反転で逆回転や補間の暴れが出る。サーバー側で角度を連続化（unwrap: 前回値との差が 180° を超えたら 360° 単位でずらす）し、range は [-360, 360] で受け止める。range は起動時固定なので、今のうちに決めておく

### 最小プロトタイプ用（S2-2 まで）: 6個

| 名前 | 用途 |
|---|---|
| vb_head_x / vb_head_y / vb_head_z | 頭の回転（pitch / yaw / roll） |
| vb_rarm_x / vb_rarm_y / vb_rarm_z | 右上腕の回転 |

### フルセット（Stage 3 で追加登録する分も含め、最初から全部定義しておく）: 約28個

- 頭 3、体幹 2（pitch / yaw）
- 右腕: 上腕 3 + 前腕 3、左腕: 上腕 3 + 前腕 3
- 右脚: 大腿 3 + 脛 3、左脚: 大腿 3 + 脛 3
- 合計 3 + 2 + 12 + 12 = 29個

※ 型の追加は再起動が必要なため、フルセットを最初から定義し、未使用分は 0 のままにする。

## ジオメトリ計画

- 人型ジオメトリを Bedrock 形式（.geo.json）で作成し、UV は **Java版スキン 64×64 の配置をそのまま再現**する（テクスチャに本人のスキン PNG をそのまま使えるようにするため）
- 本人のスキンは **classic 型（腕4px）** であることを 2026-11-24 に Mojang API で確認済み。テクスチャは `pack/skin-rk3_vivecraft.png` に取得済み
- ボーン構成（Stage 3 の関節分離を見据えた命名）:
  - root → body → head
  - body → arm_right_upper → arm_right_lower / arm_left_upper → arm_left_lower
  - root → leg_right_upper → leg_right_lower / leg_left_upper → leg_left_lower
- 最小プロトタイプでは head と arm_right_upper だけをプロパティ駆動にし、他ボーンは固定

## 進め方のメモ（ミーナのレビュー反映, 2026-11-24）

- **S2-0〜S2-2 は Altare 不要**: 手元 PC の Paper + Geyser とデモモードで回せる。Altare の障害に左右されず Stage 2 の足場固めを進められる
- **フォールバックを残す**: パックが当たらない統合版クライアントには従来の防具立て表示が出るよう、Java 側の防具立てポーズ更新は Stage 2 でも継続する（二重更新になるが安全側）
- **GeyserApi の直接呼び出しを確認する**: Geyser-Spigot は Paper と同一 JVM で動くため、Paper プラグインから `GeyserApi` を直接呼べる可能性がある。その場合、拡張は定義登録だけの薄い役割にできるかもしれない（S2-0 で確認）
- **Bedrock 側の回転合成順を確認する**: 防具立て（Z→Y→X と想定）と違う可能性がある。v0.3.1 の角度計算の符号確認と合わせて、S2-1/2 で実測する

## 前提となる運用判断

- **GeyserUpdater の自動更新を止めるか、Geyser のバージョンを固定する**（Experimental API が自動更新で壊れるリスク回避）。Stage 2 着手（S2-0）前に実施する
- スキンを変更したらパック内のテクスチャ差し替え + 再配布が必要（動的同期は不可）

## リスク・留保

- API が Experimental のため、Geyser のマイナー更新でも追従作業が発生しうる
- プロパティ約29個 × 10〜20Hz の負荷は Altare 無料枠で未実測（S2-2 で測る）
- キャリアの個別割り当てができない場合、設計の見直しが必要（S2-0 で最初に確認）


## 実装メモ（2026-11-24、しるふぁ＆ミーナのレビュー反映）

- **UUID 登録は生成前**: `world.spawn(loc, ArmorStand.class, consumer)` のコンシューマ内で UUID を登録する（エンティティがワールドに入る前なので Geyser 側イベントより確実に先行）。`setVisibleByDefault(false)` と併せて二重に安全化
- **レジストリは thread-safe に**: スポーンイベントは Geyser 側スレッドで来る可能性があるため ConcurrentHashMap 系を使う。マネキンの生成/破棄は単一のライフサイクルヘルパーにまとめ、登録解除漏れ（削除・再生成・スポーン失敗時）を防ぐ
- **クラスローダの壁（要確認）**: 同一 jar でもプラグインと拡張は別クラスローダで static は共有されない。JDK 標準型（ConcurrentHashMap 等）のインスタンス受け渡しで共有できるか S2-0 で確認する
- **スポーン直後の姿勢フラッシュ対策**: 拡張側に最新値キャッシュを持ち、スポーンイベントごとに全プロパティのスナップショットを送る（後から参加した統合版・ディメンション移動・再表示でもイベントは再発火する）
- **送信の間引き**: 変化が閾値未満（例: 0.5°）の値は送らず、batched で流す
- **S2-0 の実地確認は Altare を待たず手元 PC の Paper + Geyser で行う**（両レビュアー共通の提案）。「UUID 照合で静的ジオメトリに差し替える」だけの最小確認で、タイミング問題のほぼ全部が洗い出せる


### S2-0 実施時のチェック（2026-11-24、ミーナの助言）

1. **ログ**: スポーンイベントで受け取った UUID と、登録レジストリとの照合結果（一致/不一致）をログに出す。差し替えが効かないときに、登録タイミングの問題か照合の問題かを即切り分けできる
2. **対照実験**: 普通の防具立てを1体手動で置く。マネキンだけが差し替わり、通常の防具立てはバニラのままであることを確認する
3. **再起動確認**: Geyser を一度再起動し、再登録でも同じ結果になるか確認する

## 追記2（2026-11-24 17:15、アップデート4への しるふぁ/ミーナ レビュー反映）

### 採用した事項
- **キーは UUID に統一**（名前は改名で壊れる）。定義 ID・ファイル名は UUID 由来に変更済み。
- **登録VR一覧（roster）を単一の正**にする:`pack/roster.json` を新設し、パック生成・プラグイン・拡張が同じものを読む。
- **ジオメトリを最初から四肢2分割に作り直した**（上腕/前腕・大腿/脛、ピボットは肩・肘・股関節・膝、下側は per-face UV）。Stage 3 での作り直しを回避。per-face UV の前後（north/south）が逆でないかは S2-1 実機で確認する。
- **パック運用ルール**:事前登録制、未登録は既定スキン＋再参加で反映、再生成のたびに manifest の version を上げる、接続中クライアントへの強制再取得は不可（再接続案内で運用）。
- **slim 判定**:Mojang テクスチャ情報の `SKIN.metadata.model` の有無で判定（slim のときだけ存在）。旧 64×32 スキンの 64×64 変換は登録時の処理として明記。
- **オーバーレイ層**:RK3_Vivecraft のスキンは全オーバーレイ領域が完全透過（実測）→ 当面は未実装で進め、使用している人の登録時に inflate 付きボックス＋透過マテリアル確認とセットで追加する。

### S2-2 の実験として追加（しるふぁ提案）
- 定義を1つにし、`skin_index` / `model_type` をプロパティ化、render controller の配列を Molang `query.property` で選び分ける方式を検証する。成立すれば人の追加はパック更新のみで済み、定義ごとのプロパティ登録（29個×人数）も不要になる。
- 注意:プロパティ総数は 29+2=31。Bedrock の1エンティティあたり上限（32前後という説）の実測も S2-2 の確認項目とする。
- 最初の確認は「1本のボーンをプロパティ＋Molang で回す最小テスト」から始める。

### 保留・要確認
- `/geyser reload` が接続中セッションに与える影響（手元PCでの確認項目に追加）。
- classloader 越えの共有は JDK 型のみ（ConcurrentHashMap<UUID,Integer>、spawn コンシューマ内でマネキン→skin_index まで解決）。最終手段として System.getProperties() 経由も候補に残す。

## 追記3（2026-11-24 17:21、ミーナの追加指摘を反映）

- **オーバーレイの自動判定**:登録時にスキンのオーバーレイ領域が完全透過かどうかを自動判定し、roster に `overlay_used` として記録する。判定スクリプト `pack/check_skin.py` を作成済み（64×32 旧形式の検出も含む）。RK3_Vivecraft は `overlay_used: false` を記録済み。使用している人が来たら「オーバーレイ未対応」と即座に分かる状態にする。
- **プロパティ上限の実測手順（S2-2）**:31 個（29 姿勢 + skin_index + model_type）で通るかを確認したうえで、ダミーを足して 32 個目・33 個目で何が起きるか（エラーになるか、黙って無視されるか）を観察し、結果を記録する。
