### 1. 全体前提・スコープに関する指摘

#### 【指摘1】非FBT環境における「肘・腰（waist）」データ欠落との矛盾
- **重大度**: 高
- **根拠**: 改訂背景に「非FBTプレイヤー（本人を含む）は頭と手しかデータが無い」と明記されていますが、設計書内では以下の不整合が残っています。
  1. 脚のみ「歩行スイング代用」が追加された一方、腕は `elbow.pos` 欠落時に「1セグメント近似にフォールバック」のままです。これでは非FBTプレイヤーでは Stage 3 の主目的である「肘の関節再現（S3-1）」が一切機能せず、本人の実機確認も FBT 環境無しでは実施できません。
  2. 股関節の基準に `waist` を指定していますが、非FBTでは `waist` も欠落している可能性が高いです。
- **具体的な対処案**:
  - 腕についても非FBT向けに **「頭(肩推定)・手位置・`bodyYaw` からの簡易2ボーンIK（肘を斜め後方・外側に逃がす極ベクトル固定）」** による代用計算を入れるか、あるいは「Stage 3 の肘2セグメントは FBT 専用機能（非FBTは1セグメント＋脚スイング）」と明確にスコープを切り分けてください（S3-1 の検証条件にも直結します）。
  - `waist` が無い場合の股関節・腰の基準点（例：`player.getLocation()` または `head.pos` からの垂直投影＋高さオフセット）を明記してください。

### 2. 歩行スイング代用の設計の穴（2026-11-25 改訂部分）

#### 【指摘2】「水平移動速度＝歩行」の前提が破綻する状態・異常値の考慮漏れ
- **重大度**: 高
- **根拠**: 水平移動距離・速度のみでスイングを生成すると、**騎乗中（ボート・トロッコ・馬）、エリトラ滑空、クリエイティブ飛行、水中遊泳、はしご登坂、落下・ジャンプ中**にも脚が高速でバタバタ動いてしまい、「①動き」の自然さを大きく損ないます。また、**氷上高速移動・ノックバック・テレポート**で1フレームの移動量が跳ね上がった際、位相が一気に進み振幅が上限なく破綻する恐れがあります。
- **具体的な対処案**:
  - 以下の状態ガードとクランプを追加してください。
    1. **状態判定による無効化**: `isInsideVehicle()` / `isGliding()` / `isFlying()` / `isSwimming()` / `!isOnGround()` 時は目標振幅を `0` にして減衰させる（騎乗中は可能なら座位固定）。
    2. **振幅クランプ**: 速度スケールの係数をバニラ準拠で上限 `1.0` にクランプする。
    3. **テレポート検知**: 1フレームの水平移動距離が閾値（例: `> 2.0m`）を超えた場合は「テレポート」とみなし、そのフレームの位相加算をスキップする。

#### 【指摘3】減衰・デッドゾーン・VR微小揺らぎへの対策不足
- **重大度**: 中
- **根拠**: 「振幅は速度でスケールし、静止時は0へ減衰」の計算式が未定義です。単なる速度比例では停止瞬間に脚がワープし、単純な毎フレーム減衰では更新周期（10Hz等）に依存して減衰時間が変わります。またVRでは棒立ちでも HMD や位置基準が数ミリ〜数センチ揺れるため、微小速度を拾って脚が小刻みに震え続けるリスクがあります。
- **具体的な対処案**:
  - **デッドゾーン設定**: 水平速度が閾値未満（例: `< 0.15 m/s`）なら目標振幅を `0` とみなす。
  - **時間依存の指数平滑化**: `amp += (targetAmp - amp) * (1 - Math.exp(-k * dt))` のように `dt` 依存で減衰させ、停止直後は位相を進めず振幅のみ0へ戻す（`amp < 0.01` で位相を `0` または直立近傍へリセット）。
  - **参照元の明確化**: VRのルームスケール歩行とジョイスティック移動の双方を拾うため、移動量は `player.getLocation()` ではなく胴体基準点（または両者の整合が取れる側）に統一する。

#### 【指摘4】脛（すね）の「簡易屈曲」の位相・計算式が曖昧
- **重大度**: 中
- **根拠**: 「前に振る局面で軽く曲げる」という記述だけでは、大腿角が前方（`angle > 0`）のときに曲げるのか、後ろから前へ振り出す途中（角速度が前向き＝遊脚期）に曲げるのか不明です。前者の場合、前に踏み出した状態で停止・減衰する際に膝が曲がったまま残り不自然になります。また、`if (angle > 0)` のような分岐では境界で不連続（カクつき）が起きます。
- **具体的な対処案**:
  - 位相 `phase` に対し、振り出し中間（遊脚期）でピークになり着地・立脚期で0になる連続関数で定義してください。  
    例：大腿角を `amp * A * sin(phase)` とするなら、脛屈曲角は `amp * B * max(0, cos(phase))` または `amp * B * (1 + cos(phase)) * 0.5` のように `phase` と `amp` に連動させ、連続微分可能かつ `amp → 0` で自動的に `0°` へ収束する式にしてください。

#### 【指摘5】Stage 1 防具立てへのスイング流用における座標系・構造差の未整理
- **重大度**: 中
- **根拠**: Stage 1 の防具立ては「膝なし（1セグメント）」であり、かつ Java 版 `ArmorStand` の `LeftLegPose`/`RightLegPose` は Bedrock カスタムエンティティと軸の向き・回転方向・Euler順序が異なる可能性があります。
- **具体的な対処案**:
  - スイング生成ロジックを「大腿スイング角（スカラー）＋脛屈曲角（スカラー）」を返す共通ジェネレータとして分離し、Stage 1 は大腿角のみを `ArmorStand` のピッチ軸（符号調整済み）へ適用、Stage 2 は大腿＋脛を Bedrock ボーンへ適用する責務分離を明記してください。

### 3. 実データ ⇔ 代用の切替で起こりうる問題

#### 【指摘6】トラッキング瞬断・部分欠損時のチャタリングと急変ワープ
- **重大度**: 高
- **根拠**: FBTトラッカーは遮蔽・通信瞬断・特定姿勢で一時的にロストします。「メタデータの有無」で毎フレーム即時切替を行うと、ロストと復帰のたびに「実ポーズ（例：膝立ち・しゃがみ）」⇔「歩行スイング（直立近傍）」が1フレームで切り替わり、激しいチラつき・ワープが発生します。さらに、VSE側が非FBT・ロスト時に「nullを送る」のか「`(0,0,0)` や前回値固定を送る」のか、あるいは片脚のみロストした場合に左右バラバラのモードになるのかが未定義です。
- **具体的な対処案**:
  - **有効性判定の厳格化**: S2-3 で非FBT/ロスト時の VSE 送信値（null / ゼロ座標 / 固定値）を確認し、「両足＋両膝がすべて有効かつ妥当な距離範囲にある場合のみ FBT 実データ」と一括判定にする（片脚だけスイングになる不整合を防ぐ）。
  - **ヒステリシスの導入**: 「連続 0.5秒間 欠損したら代用へ移行」「連続 0.3秒間 安定受信したら FBT へ復帰」のように状態遷移に時間閾値を設ける。
  - **クロスフェード**: モード切替後の 0.2〜0.3秒間は実データ姿勢と代用姿勢をクォータニオン SLERP（または角度補間）でブレンドし、ワープを防ぐ。

### 4. 設計書全体で気になる点

#### 【指摘7】10Hz 同期での歩行スイングのエイリアシングと `unwrap` の破綻・発散
- **重大度**: 高
- **根拠**: 同期目標は 10Hz（100ms 間隔）ですが、ダッシュ時の歩行周期は 1〜1.5Hz 以上、脛の屈曲はその倍の周波数成分を持ちます。10Hz で角度値を直接サンプリング送信すると、ピークが削られて動きがカクつく／不規則に見えるリスクがあります。また、`unwrap` はフレーム間差分が ±180° 以内を前提としているため、100ms 間に手を高速で振ったり FBT 切替が起きると逆回り補間が発生します。さらに連続プレイで `unwrap` 値が数万度へと発散し、Bedrock プロパティの範囲制限や float 精度劣化を招く懸念があります。
- **具体的な対処案**:
  - 歩行スイングについては、サーバーから角度そのものを 10Hz で送るのではなく、**「歩行有効フラグ・移動速度（または位相増分）」のみを同期し、Bedrock 側のアニメーションコントローラ／Molang で 60fps 描画計算する**方式が Stage 2 の 29 プロパティ設計と両立できるか検討してください。10Hz 直接送信を維持する場合は「補間前提で角速度上限を制限する」妥協点を明記してください。
  - `unwrap` は「無制限に累積する角度」ではなく、Bedrock 側の補間仕様を確認した上で「静止時や周期境界で安全にリセットする」または「クォータニオンベース／`±180°` 正規化＋クライアント側最短補間」に寄せられないか S2-1/2 で検証してください。

#### 【指摘8】ツイスト決定方針（「前フレーム最短弧＋基準へ緩く戻す」）のホロノミー累積
- **重大度**: 中
- **根拠**: 「前フレームの回転からの最短弧」を連続適用する手法は幾何学的に平行移動（Parallel Transport）となるため、腕を円錐状に回すと物理的に**ツイストが累積してねじれていきます**。また、「基準へ緩く戻す」の「基準」が Rest Pose（真下）からの最短弧だと、真上（180°）付近を維持した際に基準方向自体が不連続に反転し続けます。そもそも肘が曲がっている状態では、解剖学的に上腕ツイストは「肘平面の法線（`du × df`）」で一意に決まります。
- **具体的な対処案**:
  - ツイスト決定を「候補」ではなく**優先度付きルール**として確定してください。
    1. 屈曲角が閾値以上（例: `>= 15°`）のときは、**肘平面の法線（`normalize(du × df)`）を第一優先**として上腕ツイストを直接決定する（これによりねじれ累積が原理的にゼロになり、肘の曲げ方向と上腕メッシュの向きが必ず一致する）。
    2. 伸びきり付近（`< 15°`）のみ肘平面が不安定になるため、法線の重みを下げて「前フレーム維持 ＋ 体幹基準の自然なツイスト（真上で反転しない体ローカル前方ベクトル投影等）への緩やかな減衰」へフォールバックする。

#### 【指摘9】解剖学的クランプの「再構築手順」と「デッドゾーン」の定義漏れ
- **重大度**: 中
- **根拠**: 「屈曲 0〜160° の範囲外はクランプ」とありますが、角度をクランプした後に前腕回転 `R_f`（または `R_f_rel`）をどう再構築するのかが書かれていません。また、「伸びきり付近はデッドゾーンを持たせる」の意味が「屈曲角を 0° に強制スナップする（その場合、閾値を超えた瞬間に角度がガクッと飛ぶ）」のか「ツイスト計算のみを凍結する」のか曖昧です。
- **具体的な対処案**:
  - クランプ手順を明記してください: `du` と `df` から回転軸 `axis = normalize(du × df)` と屈曲角 `θ` を求め、`θ' = clamp(θ, 0°, 160°)` で `df_clamped = rotate(du, axis, θ')` を生成してから `R_f` を計算する。
  - デッドゾーン（例: `0°〜15°`）は「屈曲角 `θ'` 自体は 0° まで滑らかに通しつつ、上記【指摘8】の肘平面法線のブレンド率だけを 0 へ落とす領域」と定義し、角度の段差を無くしてください。

#### 【指摘10】肩オフセット計算の簡略化による破綻リスク
- **重大度**: 低
- **根拠**: 「肩 = head.pos の約0.32m下から左右」をそのまま実装すると、プレイヤーが深くお辞儀した際（頭が前傾した際）に `head.pos` ごと肩が前に飛び出し、腕が胴体から離れたりめり込んだりします。また左右オフセット幅の基準値が未記載です。
- **具体的な対処案**:
  - 首の付け根（`head.pos` から頭の向き依存のローカル下方オフセット、または体幹アンカー上端）を求め、そこから `bodyYaw` 基準で左右に一定幅（例: `±0.18m`）オフセットする式に修正してください。

### 総評
歩行スイング代用の導入は非FBT実用化に向けて必須かつ妥当な方針ですが、「非FBTでは肘やwaistも無い」点と「騎乗・飛行・トラッキング瞬断への耐性」が設計上の大きな穴となっています。まずは S2-3 で VSE の非FBT/ロスト時の出力仕様を確定させ、腕の代用範囲と切替ヒステリシス・Molang委譲の可否を固めることで、手戻りのない堅牢な実装へ進めます。
